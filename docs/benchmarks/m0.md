# M0 benchmarks (tier 1, Linux X11)

Measured on 2026-10-21 on branch `feat/m0-spike`, against the PRD §10 targets (NFR-1 to NFR-4).
This is one developer machine, not the reference hardware of the §10 measurement protocol.
Wayland, GLES and Windows were not measured.

## Machine

| | |
| --- | --- |
| CPU | Intel Core i7-8700 @ 3.20 GHz, 6 cores / 12 threads (`/proc/cpuinfo`) |
| GPU | NVIDIA GeForce GTX 1080 (GP104), driver 580.178.04; the app runs on it (`nvidia-smi` lists `plexusterm` as `C+G`, 64 MiB). An Intel UHD 630 is also present (`lspci`) |
| Displays | two 1920×1080 at 74.97 Hz (`xrandr`), so one frame is 13.3 ms |
| RAM | 15 GiB |
| OS | Linux Mint 22.3, kernel 7.0.0-38-generic, X11 session |
| Toolchain | rustc 1.98.1, release profile (`lto = true`, `codegen-units = 1`) |
| Shell | `/bin/bash` with the user's own `~/.bashrc` (`bash -i -c exit` takes 211–287 ms on its own) |

The desktop was in normal use during the runs (a browser and editors open).

## What is measured

**Key latency (NFR-1, TERM-17).** With `PLEXUS_LATENCY_LOG=<folder>`, the app writes
`<folder>/keys.log` and `<folder>/frames.log` from a writer thread (`crates/app/src/latency.rs`).

- `K`: taken in the GPUI key handler after the key was queued to the session.
- `O`: taken in `render` when a snapshot with damaged rows reaches the view while keys are waiting.
  That output counts as the echo of every waiting key.
- `F`: the frame painted from that render has been submitted. One `F` per key, with
  `key_received → frame_submitted` in µs.

How "submitted" is taken at the pinned GPUI rev (`a484d108`): the pane's paint callback runs
inside `Window::draw`. GPUI's frame callback then calls `Window::present` in the same call, which
does the renderer's draw and the surface present. The paint callback queues a foreground task.
The executor only runs it after the frame callback has returned, so `F` is taken at or after
present returned. Compositor and scan-out time are not included.

When the variable is unset, the log is `None`: one branch per key and per frame, and no
allocation. `frames.log` holds the interval between submitted frames.

**Engine throughput (NFR-2, no display).** `crates/term-engine/tests/throughput.rs` (ignored by
default) pushes 100 MiB of mixed output into a `ByteRing`. The mix is plain text, SGR
16/256/truecolor with bold, italic and underline, CJK and Hangul, and absolute and relative cursor
motion with erase. A `Session` (140×38, 10 000 lines of scrollback) parses it while a "UI" thread
calls `snapshot()` every millisecond. The test reports MiB/s and how long each `snapshot()` took.
That time is the lock wait plus the frame copy, so it is the longest the UI can be held by a
parse slice (ST-2). It also checks that the last line of the corpus reached the screen.

**App `cat` (NFR-2).** `$SHELL` is set to a script that sleeps 2 s, records the time, runs
`cat` on the same 100 MiB corpus inside the app's PTY, then records the time again. The frame
intervals inside that window come from `frames.log`.

**Startup (NFR-3).** A build with the `bench` feature honours `PLEXUS_EXIT_AFTER_FIRST_PROMPT=1`.
It quits after the first submitted frame that has any non-blank cell, and prints the time since
`main` started. The wall time from exec to exit is measured from outside. Since T6b it also prints
each startup phase and the wall clock at `main` (see "T6b" below); the first-frame rule was
corrected there.

**Memory (NFR-4).** `VmRSS` from `/proc/<pid>/status`, 10 s after launch. The prompt is up
after about 0.5 s.

## Commands

```sh
cargo build -p plexusterm --release                       # app
cargo build -p plexusterm --release --example latency_report
cargo build -p plexusterm --release --features bench      # NFR-3 build only

# engine throughput; PLEXUS_THROUGHPUT_CORPUS also writes the corpus for the app run
PLEXUS_THROUGHPUT_CORPUS=/path/corpus.txt \
  cargo test -p term-engine --release --test throughput -- --ignored --nocapture

# key latency: 600 keys through xdotool with an 80 ms gap; under load, 12 `yes > /dev/null`
docs/benchmarks/scripts/typekeys.sh $PWD/target/release/plexusterm <folder> 600 0     # idle
docs/benchmarks/scripts/typekeys.sh $PWD/target/release/plexusterm <folder> 600 12    # load
target/release/examples/latency_report <folder>

# app cat: the app quits when the script (its "shell") ends
CORPUS=/path/corpus.txt MARKS=<folder> SHELL=$PWD/docs/benchmarks/scripts/catshell.sh \
  PLEXUS_LATENCY_LOG=<folder> target/release/plexusterm
target/release/examples/latency_report <folder> $(($(cat <folder>/cat-start)/1000)) $(($(cat <folder>/cat-end)/1000))

# startup: 13 runs, the first one right after the build
PLEXUS_EXIT_AFTER_FIRST_PROMPT=1 plexusterm   # bench build, wall time via `date +%s%N`

# T6b: startup phases and memory breakdown, app and floor reference
cargo build -p plexusterm --release --features bench --bin plexusterm --example floor_window
docs/benchmarks/scripts/startup-phases.sh target/release/plexusterm 12 /bin/sh
docs/benchmarks/scripts/startup-phases.sh target/release/examples/floor_window 12
docs/benchmarks/scripts/rss-breakdown.sh target/release/plexusterm 10
```

`scripts/typekeys.sh` starts the app and finds the window owned by the app's pid whose name is exactly
`PlexusTerm`. It activates that window with `windowactivate --sync`. Before every keystroke it
checks that `getactivewindow` and `getwindowfocus` are that window and that its pid is the app's;
it stops typing on the first mismatch. The keys cycle `a`–`z`, and every 60th key is `ctrl+u`, so
the line is cleared 10 times. The script kills the app and the load at the end. The first attempt
stopped after 14 keys because the focus moved to another window (the user's browser). That
attempt checked only the active window (`getactivewindow`). The input-focus check
(`getwindowfocus`) was added before the measured runs. That attempt's `keys.log` was empty: the
writer flushed only when the log went quiet, and the app was killed before that. The writer now
also flushes every 200 ms during a steady stream.

### Notes

1. **Where the key latency goes.** The marks split each key into two parts. Key → render with
   the echo (`K → O`) is p50 5.8 ms and p95 13.1 ms, both idle and under load. That spread is
   one refresh period (13.3 ms at 75 Hz): the output waits for the next frame callback. Render,
   paint and present (`O → F`) is p50 2.0–2.9 ms, p95 3.7–5.1 ms. The PTY round trip and the
   parser take little of it. p95 ≤ 8 ms cannot be met while the echo waits for the next frame
   callback at 75 Hz and the frame then takes about 3 ms. The fix belongs in the frame path
   (present as soon as the echo arrives, within the vsync budget). The engine is not the cause.
   "Submitted before the next vsync" was not checked: the log has no vsync timestamps.
2. **CPU load does not change the picture.** 12 busy processes on 12 hardware threads add about
   0.5 ms at p95 and 1.7 ms at p99.
3. **The UI waits up to one parse slice for its snapshot during floods.** The median
   `snapshot()` time of about 3.5 ms is close to the 4 ms slice (ST-2). One run had a 12.5 ms
   maximum, more than the slice. That fits OS preemption of the parser thread while it holds
   the lock. At 75 Hz this uses about a quarter of the frame budget. It is the likely reason the
   frame interval during `cat` reaches 26–32 ms (two to three refresh periods).
4. **Startup.** About 100 ms of the gap to 300 ms is this user's `bash` startup (bash with
   `.bashrc` against `/bin/sh`). The app alone still takes about 285–440 ms before its first
   prompt frame. The breakdown (GPU/Vulkan initialisation, font loading, window mapping) has not
   been profiled yet.
5. **Memory.** RSS includes the NVIDIA user-space driver mappings. Its split between driver and
   app heap is not measured yet. The Intel GPU or the GLES path may show a different number.
6. Each "first prompt submitted" message can appear twice: a second frame can be submitted
   before the quit takes effect. Only the first one counts.

## T6b: startup (NFR-3) and memory (NFR-4)

Measured on 2026-10-21, same machine. **The machine was loaded** during these runs: other builds
(`rustc`, `rust-lld`) kept the load average at 6.5–12 on 12 threads. Startup spreads are wide
because of that; the comparisons below interleave the binaries run by run, so they share the load.

### Method

- `bench` builds print `plexusterm: main at <µs since the epoch>` and one
  `plexusterm: phase <name> <µs since main>` line the first time each phase is reached
  (`crates/app/src/startup.rs`). The launcher records the epoch before `exec`, so
  **exec → first prompt frame = (main at − launcher epoch) + first prompt µs**. The old "wall"
  number also counted process teardown after the quit (60–75 ms of GPU driver teardown), which
  NFR-3 does not include. The script is `scripts/startup-phases.sh`.
- **First-frame rule, corrected.** At this GPUI rev `open_window` draws the view once and does not
  present it. The first frame callback presents that scene, and redraws first only if the window
  is dirty. The old exit hook queued its task from that first paint, and it could run before any
  present. It did not in the "before" runs, because the pane's first frame asked for a resize and
  so forced a second, presented frame first. The pane now reports its first paint from the next
  frame callback (`window.on_next_frame`), and the task runs after that callback has presented.
  The floor reference uses the same rule.
- **Floor reference**: `crates/app/examples/floor_window.rs`, with the same GPUI rev and window
  options as the app, and one filled `div`. It has no terminal, PTY, font or text. It prints the
  same lines.
- **Memory**: `VmRSS` and `/proc/<pid>/smaps` 10 s after launch, with Rss summed per mapping. GPU
  memory comes from `nvidia-smi --query-compute-apps=pid,used_memory`. The script is
  `scripts/rss-breakdown.sh`.
- **Driver experiments**, which change nothing in the repository: `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/nvidia_icd.json`
  makes the Vulkan loader load only the NVIDIA driver. "Vulkan only" is a scratch copy of the
  pinned Zed checkout with one line changed in `gpui_wgpu::WgpuContext::instance`
  (`Backends::VULKAN` instead of `VULKAN | GL`), used through `[patch]` by a scratch copy of
  this repository.

### Phase breakdown (app, `/bin/sh`, 12 runs, medians, ms since `main`)

| Phase | Before | After | What happens |
| --- | --- | --- | --- |
| exec → `main` | 2.1 | 2.4 | dynamic loading |
| PTY spawned | 19.2 | **1.1** | now before `gpui_platform::application()` (ST-7) |
| GPUI app created | 12.9 | 14.4 | X11 connection, fontconfig, system font scan |
| run callback | 17.5 | 19.2 | |
| view constructed (inside `open_window`) | 305.4 | 283.1 | X11 window, wgpu instance, adapter enumeration, device, surface: **≈ 265 ms** |
| font picked + measured | +4.7 | +8.9 | |
| first paint done (inside `open_window`) | 314.1 | 301.2 | |
| prompt frame presented | 332.3 | 348.1 | first frame callback presents; 20–50 ms after the paint |
| process teardown after the quit | ≈ 70 | ≈ 67 | not part of NFR-3 |

The terminal's own work is font lookup and measurement (5–9 ms) plus the first render and paint
(1–10 ms). Everything else belongs to the GPUI window and the GPU driver. `strace` of the floor
shows that window setup loads the Vulkan loader. That loader loads **every installed ICD**
(Intel, hasvk, nouveau, radeon with `libLLVM`, asahi, virtio, gfxstream, lavapipe), then
the NVIDIA driver. It then loads the whole EGL stack, NVIDIA's and Mesa's with
`libgallium` (wgpu's GL backend is enabled next to Vulkan). Mesa's EGL fails on the NVIDIA
device, as the `libEGL warning: egl: failed to create dri2 screen` lines show.

Other rows: app before 196.9 / 196.5 MB, app + `VK_DRIVER_FILES` 179.0 / 179.2 MB, and floor

appear with the first text.

### Changes in T6b and their measured effect

| Change | Effect |
| --- | --- |
| PTY spawned before GPUI starts (`main.rs`) | spawned at 1.1 ms instead of 19 ms; the bash prompt now arrives before the window's first draw ends |
| Pane asks for its real grid size before the first frame (`initial_grid`) | the resize-and-second-frame at startup is gone (`resize_refresh` no longer appears); the shell gets its size before its first prompt |
| First paint reported from the next frame callback | the measurement is valid, not a speed change |
| Phase marks (`bench` only), `floor_window` example | measurement only |

The before/after medians are within the load noise. These changes take the terminal off the
critical path. They do not change the floor it sits on.

### Verdict

| Target | Result | Verdict |
| --- | --- | --- |
| NFR-3 ≤ 300 ms warm, exec → first prompt frame | app 312–350 ms median (`/bin/sh` or bash); empty GPUI window 340 ms | **missed, at the floor**: an empty GPUI window at this rev does not meet it on this machine. With GL off and only the NVIDIA ICD loaded, the floor is 212 ms |
| NFR-4 ≤ 120 MB RSS 10 s after the prompt | app 196.7 MB; empty GPUI window 193.2 MB | **missed, at the floor**: 74 % of the app's RSS is GPU driver code that GPUI loads (all Vulkan ICDs, wgpu's GL backend). With GL off and only the NVIDIA ICD, the floor is 97.6 MB, so the app would be about 101 MB |
| GPU memory | 64 MiB | reported (floor 32 MiB) |

Both targets need a decision outside the terminal code: wgpu's instance at the pinned rev is
`VULKAN | GL` with no setting to change it, so turning GL off means patching or forking
`gpui_wgpu`. Loading only the right Vulkan driver needs `VK_DRIVER_FILES`, or the loader's
driver selection, set before GPUI starts. The app cannot set it in-process
(`std::env::set_var` is `unsafe` in edition 2024, and the crate forbids unsafe code). A launcher
or a re-exec could set it, and it has to pick the GPU the compositor uses.

## Not measured in M0 tier 1

Wayland, Vulkan against GLES, Windows D3D11, 10 000-keystroke runs with `cargo build` in the
background (the §10 protocol), vtebench, Ctrl+C acknowledgement under flood, scrolling fps, and
the extra RSS per terminal.
